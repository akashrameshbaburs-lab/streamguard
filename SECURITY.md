# Security Policy

## Scope

StreamGuard is a portfolio fraud-detection pipeline intended to run **locally
via Docker** against synthetic payment events. It is not hardened for public
internet exposure.

## Supported versions

Only the latest commit on `main` receives fixes.

## Data-handling model

- All events are synthetic (generated by the simulator or `scripts/synth.py`);
  no real cardholder data is present anywhere in this repository.
- The training pipeline (`scripts/train.py`) trains only on the local
  Postgres `events` table; the model artifact stays in the `MODEL_DIR` volume.
- Notifications are optional: with `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`
  unset, the notifier stays healthy and alerts remain API/database-only.

## Production-hardening checklist

The `.env.example` values are development defaults. Before pointing this at
real event data, change at least:

| Variable | Why |
| --- | --- |
| `PG_DSN` | Dev credentials (`streamguard:streamguard`) are public in this repo |
| `AMQP_URL` | Same — RabbitMQ dev credentials are public in this repo |
| `TELEGRAM_BOT_TOKEN` | Treat as a secret; never commit a real token |
| `ALERT_THRESHOLD` / `ML_WEIGHT` / `FUSION_GAMMA` | Re-tune on a real labelled dataset — the committed values are the optimum for the *synthetic* data only (see `docs/METRICS.md`) |

Additional notes:

- The RabbitMQ management UI (port 15673) and Postgres (5435) are published
  for local debugging only; bind them to loopback or drop the port mappings
  for anything beyond a single machine.
- Alert feedback (`POST /api/alerts/:id/feedback`) is unauthenticated by
  design in the demo; any real deployment must put the API behind authn/z.
- The consumer trusts events on the queue: a real deployment should authenticate
  AMQP publishers and validate event schemas at the boundary.

## Reporting a vulnerability

Please open a GitHub issue describing the issue and steps to reproduce. Issues
labeled `security` take priority.
